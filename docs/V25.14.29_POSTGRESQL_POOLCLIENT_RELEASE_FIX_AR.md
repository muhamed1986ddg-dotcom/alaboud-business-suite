# v25.14.29 — إصلاح تسريب اتصالات PostgreSQL

## السبب الجذري
في v25.14.28 كان مسارا `queryWithRetry()` و `save()` يستدعيان `isConnectionError(attemptError)` داخل `finally`، لكن الدالة لم تكن معرفة في الملف. لأن الاستدعاء كان داخل `try/catch` صامت، كان `ReferenceError` يُبتلع ولا يصل التنفيذ إلى `client.release(...)`.

النتيجة: كل استعلام ناجح يستطيع إبقاء `PoolClient` محجوزًا بدل إعادته إلى `pg.Pool`. بعد امتلاء الـ pool تظهر `PG_CLIENT_HARD_TIMEOUT` رغم أن Cloud SQL نفسه متاح وعدد الاتصالات أقل بكثير من `max_connections`.

## الإصلاح
- إضافة `isConnectionError()` بشكل صريح.
- إعادة العميل السليم إلى pool بعد كل قراءة/كتابة ناجحة.
- تدمير العميل فقط عند أخطاء اتصال حقيقية (`08xxx`, انقطاع socket، `PG_CLIENT_HARD_TIMEOUT`, shutdown/recovery).
- عدم اعتبار أخطاء SQL مثل `57014` و `55P03` بحد ذاتها دليلًا على socket تالف.
- إضافة اختبار regression يمنع رجوع نفس الخطأ.

## التحقق المتوقع بعد النشر
بعد تشغيل الواجهة يجب أن لا يبقى `poolIdle=0` باستمرار. يجب أن تعود اتصالات إلى حالة idle داخل pool، وأن تختفي `durable-write-connect hard timeout` الناتجة عن استنزاف PoolClient.
