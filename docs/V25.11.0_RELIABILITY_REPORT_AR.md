# تقرير v25.11.0 — الاعتمادية والاسترجاع

## التغييرات المنفذة

1. **إعادة اتصال PostgreSQL**
   - تتبع حالة الاتصال: `connected / connecting / reconnecting`.
   - تسجيل آخر اتصال وانقطاع وآخر خطأ وعدد الإخفاقات المتتالية.
   - إعادة إنشاء Pool تلقائيًا عند أخطاء الاتصال العابرة.

2. **إعادة المحاولة الذكية**
   - الاستعلامات والكتابات تستخدم exponential backoff مع jitter وميزانية زمنية.
   - العمليات الدائمة لا تعيد نجاحًا قبل قبول PostgreSQL للـ snapshot.
   - عند استنفاد المحاولات يعود 503 برسالة عربية تؤكد عدم حفظ التغيير.

3. **منع تكرار العمليات**
   - إضافة `Idempotency-Key` تلقائيًا لكل POST/PUT/PATCH/DELETE.
   - الخادم يمنع الطلب المكرر أثناء التنفيذ، ويعيد النتيجة السابقة عند تكرار المفتاح بعد النجاح.
   - مدة الاحتفاظ الافتراضية 5 دقائق، قابلة للضبط بالبيئة.

4. **مؤشر حالة قاعدة البيانات**
   - فحص `/api/health` كل 45 ثانية.
   - لا يظهر شيء في الحالة الطبيعية.
   - يظهر تنبيه أصفر أثناء إعادة الاتصال وأحمر عند الانقطاع.

5. **رسائل أخطاء واضحة**
   - تمديد مهلة الكتابة في العميل إلى 20 ثانية لتجنب فشل وهمي أثناء retry.
   - رسائل خاصة بانقطاع PostgreSQL وعدم إعادة الضغط.
   - إظهار Request ID من الخادم لتسهيل تتبع الخطأ في السجلات.

6. **سجل التدقيق والمعاملات**
   - سجل التدقيق المتسلسل والموقع بالـ hash الموجود في النظام ما زال يسجل العمليات الحساسة داخل نفس snapshot الدائم.
   - حفظ `app_state` يتم عبر UPSERT ذري واحد؛ إما يُقبل snapshot كاملًا أو لا يُحفظ أي جزء منه.
   - الإسقاط العلائقي يبقى مرآة تقارير غير حاجبة ولا يحدد نجاح العملية الأساسية.
